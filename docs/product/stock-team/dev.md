# 주식 투자 에이전트 팀 개발 스펙

> 기준 문서: [기획 PRD](prd.md) · [기획 상세 스펙](spec.md) · [유저 플로우](flow.md) · [개발 스펙](dev.md)

## 결정 기록

### <a id="d1"></a>D1 서버는 Rust 한 프로그램으로 다시 만들고 3D 사무실 화면만 웹으로 둔다

이유: 메모리 문제 때문에 Python 에이전트 실행기와 Node 사무실 서버를 그대로 쓰지 않는다. 집 PC와 미니 PC에서도 24시간 가볍게 돌아야 한다.
버린 대안: Hermes Agent와 DeskRPG를 그대로 올려 확장하기, Hermes만 Rust로 바꾸기, 화면까지 Rust(WASM)로 만들기.
출처: 제약 › 집 PC, 노트북, 미니 PC의 모든 운영체제와 빌린 원격 컴퓨터에서 돌아야 한다.

### <a id="d2"></a>D2 기본은 그 컴퓨터에서만 열고 다른 기기는 접속 키로만 들어온다

이유: 본인만 쓰고 주로 로컬에서 쓴다. 밖에서 닿게 하는 길(Tailscale 등)은 사용자가 알아서 하므로 스펙에 넣지 않는다. Hermes와 OpenClaw의 기본값(자기 컴퓨터 주소에만 열기)과 같다.
버린 대안: Tailscale을 스펙에 넣기, OTP(인증 앱 6자리), VPN 켜고 끄기, 접속 키 없이 열기.
출처: 제약 › 나 혼자만 쓴다.

### <a id="d3"></a>D3 증권사 키와 AI 키는 Hermes 방식대로 홈 폴더의 파일에 본인만 읽는 권한으로 둔다

이유: API 키는 .env 파일에, 구독 OAuth 토큰은 auth.json에 0600 권한과 원자 쓰기로 둔다. 모든 운영체제와 원격 컴퓨터에서 같다. 화면과 기록과 AI 대화에는 다시 내보내지 않고 백업에서 뺀다.
버린 대안: OS 키체인(화면 없는 Linux에서 다르게 동작한다), DB에 저장, 백업에 포함.
출처: 제약 › 증권사 키와 AI 키는 내가 직접 등록한다.

### <a id="d4"></a>D4 AI는 Rust의 공급자 어댑터로 부른다. API 키는 직접 부르고, 구독은 공식 Claude Code CLI를 불러 쓴다

이유: API 키는 호출마다 프로세스를 띄우지 않아 빠르고 가볍다. 구독은 토큰을 우리가 쥐지 않고 사용자가 로그인한 공식 CLI에 맡긴다(구독 토큰을 다른 프로그램이 API에 직접 쓰는 것은 Anthropic이 금지). 각자 자기 컴퓨터에서 자기 AI 로그인을 세팅해 쓸 수 있다.
버린 대안: 구독 OAuth 토큰을 API 키와 같은 자리에 끼워 API에 직접 보내기(2026-11-15 사용자 결정으로 바꿈, `docs/dev/decisions.md`).
출처: 제약 › 각자 자기 컴퓨터에서 자기 로그인을 세팅해 쓸 수 있어야 한다.

### <a id="d5"></a>D5 시세와 주문과 장 시간과 시장별 원칙 값은 시장 어댑터로 나눈다

이유: 국내 주식과 미국 주식(토스증권)을 먼저 붙이고, 코인은 어댑터 하나를 더해 붙인다. 에이전트와 규칙 엔진은 시장을 몰라도 된다.
버린 대안: 지금은 주식에만 맞춰 만들고 코인 때 따로 설계하기.
출처: 제약 › 나중에 코인을 더할 수 있게 만든다.

### <a id="d6"></a>D6 상태와 매매 기록과 복기와 지식은 SQLite 파일 하나에 둔다

이유: 따로 설치할 것이 없고 모든 운영체제에서 같다. 전문 검색(FTS5)으로 기억을 찾고, 백업 API로 일관된 스냅샷을 뜬다.
버린 대안: PostgreSQL(따로 설치 · 운영하고 메모리를 더 쓴다).
출처: [D1](#d1)

### <a id="d7"></a>D7 매일 장 마감 뒤 SQLite 스냅샷을 age로 암호화해 private GitHub 저장소에 올린다

이유: 컴퓨터가 고장 나도 상태와 템플릿과 지식을 되살린다. 서버에는 공개키만 두고 푸는 열쇠는 GitHub 밖에 둔다.
버린 대안: 평문 private 저장소, git-crypt.
출처: [D6](#d6)

### <a id="d8"></a>D8 12월 최종 발표까지 [P1](prd.md#p1)과 P2 요구사항을 모두 돌아가게 한다

이유: 본인이 전부 12월까지 하기로 정했다.
버린 대안: [P1](prd.md#p1)과 모의투자만 먼저 하고 3D 사무실과 폰 화면은 발표에 필요한 만큼만.
출처: 제약 › 12월 최종 발표까지 나와야 한다.

### <a id="d10"></a>D10 지식은 에이전틱 RAG로 다루고, 키워드 · 조건 검색을 먼저 넣고 뜻 검색(벡터)은 공급자를 고른 뒤 붙인다

이유: 시세와 뉴스와 매매 기록은 실시간으로 많이 바뀌어 정리된 위키 페이지는 금방 낡는다. 담당이 판단할 때 검색 도구로 직접 찾는다. 키워드 검색과 조건 검색과 뜻 검색을 함께 쓰고, 임베딩은 AI 공급자 어댑터로 만들어 SQLite에 둔다. 승인된 규칙은 검색하지 않고 규칙 엔진의 확정값으로 둔다.
버린 대안: LLM 위키(에이전트가 페이지를 써서 유지).
바뀜 (2026-11-16, 사용자 결정): 원래는 "뜻 검색을 처음부터"였다. AI 공급자(Anthropic)가 임베딩을 주지 않아, 뜻 검색 자리(포트)만 먼저 두고 키워드 · 조건 검색부터 쓴다. 뜻 검색은 사용자가 임베딩 공급자를 고른 뒤 붙이고, 그 전에는 "쓸 수 없음"으로 돌려준다(`docs/dev/decisions.md` 2026-11-16 11번).
출처: [R8-1](prd.md#r8-1)

### <a id="d11"></a>D11 화면과 서버는 WebSocket 하나로 실시간을 주고받고 요청은 REST로 보낸다

이유: 채팅과 담당 움직임과 알림과 승인 요청을 한 연결로 받고, 끊기면 마지막으로 받은 번호부터 이어 받는다. 폰의 가벼운 화면과 3D 사무실이 같은 연결을 쓴다. 화면의 모든 요청은 접속 관문을 거친다.
버린 대안: SSE와 REST로 나누기, Socket.IO.
출처: [F7](spec.md#f7) › 대안 흐름 › 1a. 사용자가 폰에서 가격인하를 연다 › 1a2. 사용자가 3D 사무실을 누르면 사무실 화면이 열린다

### <a id="d9"></a>D9 재무 · 거시 · 뉴스 · 공시 자료는 공식으로 무료로 쓸 수 있는 API로만 가져온다

이유: 비용 없이 쓰고 출처가 분명해야 한다. 후보는 DART 오픈API(국내 공시 · 재무), 한국은행 ECOS와 미국 FRED(거시), SEC EDGAR(미국 공시 · 재무), 무료 뉴스 검색 API와 토스증권이 주는 자료다. 각 API 키는 본인이 등록한다.
버린 대안: 유료 데이터 서비스, 웹 페이지 긁어 오기, 토스 API 하나에만 기대기.
출처: [R12-2](prd.md#r12-2), [R12-3](prd.md#r12-3), [R12-4](prd.md#r12-4)

### <a id="d12"></a>D12 담당 부르기 · 멘션 걸어오기는 서버가 단계만 정하고 길은 화면이 찾는다

이유: 서버는 지도를 모르고 자리 이름만 보낸다(office 지시서). 원본 DeskRPG도 걷기는 브라우저가 계산하고 서버는 단계와 주인만 기록한다. 우리는 사용자가 한 명이라 "주인" 개념은 필요 없다. 서버는 자리 · 오는 중 · 곁에서 기다림 · 돌아가는 중 단계와 시각을 쥐고, 화면이 도착을 알린다.
버린 대안: 서버가 지도를 알고 길까지 계산하기(지도 자료를 서버에 들여야 하고 원본과도 다르다).
출처: [F10](spec.md#f10) › 대안 흐름 › 4c. 사용자가 담당 목록에서 "부르기"를 누른다

### <a id="d13"></a>D13 근거 카드 칸은 담당 점수를 바꾸지 않고 옆에 더한다

이유: 잠긴 시험과 옛 매매를 지키려고 담당 점수(담당 · 점수 · 근거)는 그대로 두고, 방향 · 확신도 · 보는 기간 · 기권과 팀장 요약 · 뒤집힐 조건을 새 칸으로 붙인다. 옛 매매는 "기록 없음"이다. 확신도는 3등급(낮음 · 보통 · 높음)으로 둔다(투자 에이전트 팀 조사 F 1).
버린 대안: 점수 부호로 방향을 추정하기(기권과 중립을 가릴 수 없다).
출처: [R6-4](prd.md#r6-4)

### <a id="d14"></a>D14 시연 모드는 자기 달력을 쓴다

이유: 시연용 가짜 증권사가 달력을 정하지 않아 늘 휴장이고 깨우기 엔진 첫 tick이 503으로 실패한다. 시연 달력은 매일을 거래일로 보고 시장 시간대 00:05~23:55를 정규장으로 둔다. 자정 앞뒤 10분은 장 밖이라 하루 시작 · 장 마감 뒤 일(하루 정리 · 복기 · 정산)이 매일 돈다. 시연 모드에서만 쓰고 실제 모드에서는 쓰지 않는다.
버린 대안: 늘 열림(장 마감 뒤 일이 돌지 않는다), 실제 장 시간(밤 시연에서 팀이 쉰다), 시연 단추로 장 마감 부르기(화면과 길이 하나 더 는다).
출처: [R2-3](prd.md#r2-3)

## 데이터 모델

### <a id="m1"></a>M1 투자 팀

| 값 | 뜻 | 규칙 |
|---|---|---|
| 상태 | 상태표의 투자 팀 상태 | 운용 중, 쉬는 중, 하루 한도 멈춤, 이상 감지 멈춤, 전체 정지 중 하나다 |
| 그날 손실 | 그날 실현 손실과 평가 손실 | 거래일마다 새로 센다 |
| 최고점 대비 손실 | 계좌 최고 평가액 대비 손실 | 템플릿 한도와 비교한다 |
| 정지 사유 | 전체 정지가 된 까닭 | 최대 손실 또는 내가 정지(결정 25) 중 하나다 |

전체 정지로 들고 나는 전이(결정 20 · 25)

| 앞 상태 | 뒤 상태 | 사유 | 누가 |
|---|---|---|---|
| 운용 중 | 전체 정지 | 최대 손실 | 자동 규칙 |
| 쉬는 중, 운용 중, 하루 한도 멈춤, 이상 감지 멈춤 | 전체 정지 | 내가 정지 | 나(계좌 화면의 "전체 정지" 단추 · 메신저 `/stop`, [C35](#c35)) |
| 전체 정지 | 쉬는 중 | 다시 시작 | 나(계좌 화면에서 누르고 확인, [C8](#c8)) |

- 전체 정지에서 다른 상태로는 내 승인으로만 바뀐다.
- 내가 정지로 가는 전이는 "내 승인" 표시가 있을 때만 받는다. 담당(AI)은 정지를 부르지 못한다. 메신저로는 정지만 되고 다시 시작은 되지 않는다.
- 하루 한도 멈춤은 다음 거래일 시작 때만 풀린다.
- 상태가 바뀔 때마다 언제 왜 바뀌었는지 기록이 남는다.

출처: 기획 상세 스펙 › 상태표 › 투자 팀

### <a id="m2"></a>M2 매매

| 값 | 뜻 | 규칙 |
|---|---|---|
| 상태 | 상태표의 매매 상태 | 논의중, 판단됨, 승인대기, 막힘, 주문됨, 보유중, 팔림, 복기됨 중 하나다 |
| 근거 | 가설과 계기와 들어간 값과 손절값과 목표값과 기대값 | 하나라도 비면 주문됨으로 갈 수 없다 |
| 자료 시각 | 판단에 쓴 자료마다 알게 된 시각 | 판단 시각보다 늦을 수 없다 |
| 담당 점수 | 담당별 점수와 근거와 합의 점수 | 판단됨이 될 때 함께 남는다 |
| 계좌 종류 | 모의 또는 실전 | 실전은 실전중 템플릿에서만 나온다 |
| 승인 | 승인 번호와 승인한 내용의 지문 | 실행할 내용의 지문과 다르면 주문하지 않는다 |

- 보유 중 손절값은 좁히기만 할 수 있다.
- 손실 중인 종목에 더 사는 매매는 만들 수 없다.

## 오류·경계

### <a id="e1"></a>E1 접속 키 틀림

상황: 다른 기기에서 넣은 접속 키가 맞지 않는다.
보이는 것: 접속 키가 틀렸다는 안내가 보인다.
시스템 처리: 실패 횟수를 올리고 세션을 만들지 않는다.
출처: [F8](spec.md#f8) › 대안 흐름 › 1b. 접속 키가 맞는가: 아니오

### <a id="e2"></a>E2 접속 잠금

상황: 접속 키를 정한 횟수보다 많이 틀렸다.
보이는 것: 한동안 시도할 수 없다는 안내가 보인다.
시스템 처리: 그 기기의 시도를 한동안 막고 나에게 알림을 보낸다.
출처: [F8](spec.md#f8) › 예외 흐름 › 1c. 접속 키를 여러 번 틀린다

### <a id="e3"></a>E3 연결 끊김

상황: 화면과 집 컴퓨터의 연결이 끊긴다.
보이는 것: 연결이 끊겼다는 안내와 마지막으로 받은 상태가 보인다.
시스템 처리: 팀의 운용은 그대로 이어지고 다시 이어지면 놓친 이벤트부터 보낸다.
출처: [F7](spec.md#f7) › 예외 흐름 › 1b. 집 컴퓨터에 연결되지 않는다

### <a id="e4"></a>E4 키 확인 실패

상황: 넣은 키로 증권사나 AI에 닿지 않는다.
보이는 것: 키가 맞지 않다는 안내가 보인다.
시스템 처리: 그 키를 저장하지 않는다.
출처: [F6](spec.md#f6) › 예외 흐름 › 1a. 키 등록이 실패한다

### <a id="e5"></a>E5 상한 넘는 값

상황: 템플릿 값이 원칙 상한을 넘는다.
보이는 것: 그 값은 저장되지 않고 상한이 보인다.
시스템 처리: 이전 값을 그대로 둔다.
출처: [F6](spec.md#f6) › 대안 흐름 › 3a. 사용자가 원칙 상한을 넘는 값을 넣는다

### <a id="e6"></a>E6 담당 응답 실패

상황: 담당이 AI 응답을 받지 못한다.
보이는 것: 그 담당이 답하지 못했다는 표시가 보인다.
시스템 처리: 논의 중이면 팀장이 지켜보기로 정한다.
출처: [F2](spec.md#f2) › 예외 흐름 › 5a. 담당 하나가 답하지 못한다

### <a id="e7"></a>E7 승인한 내용이 바뀜

상황: 승인한 내용의 지문과 실행할 내용의 지문이 다르다.
보이는 것: 그 일이 진행되지 않았다는 안내가 보인다.
시스템 처리: 거절로 남기고 실행하지 않는다.
출처: [FN2](spec.md#fn2) › 예외 흐름 › 4a. 승인한 뒤 실행할 내용이 바뀌었다

### <a id="e8"></a>E8 승인 확인 실패

상황: 승인 번호가 없거나 이미 처리됐거나 만료됐다.
보이는 것: 이미 처리됐거나 만료됐다는 안내가 보인다.
시스템 처리: 거절로 남기고 팀이 대신 판단하지 않는다.
출처: [FN2](spec.md#fn2) › 예외 흐름 › 3c. 승인 확인이 실패한다

### <a id="e9"></a>E9 다시 시작 못 함

상황: 되살린 뒤 키를 다시 등록하지 않았다.
보이는 것: 키를 먼저 등록하라는 안내가 보인다.
시스템 처리: 투자 팀은 멈춘 상태로 남는다.
출처: [F9](spec.md#f9) › 대안 흐름 › 1a. 사용자가 새 컴퓨터에서 백업을 되살린다 › 1a1. 투자 팀은 멈춘 상태로 시작한다

### <a id="e10"></a>E10 근거 부족

상황: 주문 안에 근거가 빠져 있다.
보이는 것: 사무실과 폰에 막힌 이유가 보인다.
시스템 처리: 주문을 막고 빠진 근거를 남긴다.
출처: [FN1](spec.md#fn1) › 대안 흐름 › 1a. 근거가 다 있는가: 아니오

### <a id="e11"></a>E11 원칙 위반

상황: 주문 안이 기본 원칙을 어긴다.
보이는 것: 사무실과 폰에 막힌 이유가 보인다.
시스템 처리: 주문을 막고 어긴 원칙을 남긴다.
출처: [FN1](spec.md#fn1) › 대안 흐름 › 2a. 원칙을 지키는가: 아니오

### <a id="e12"></a>E12 미체결

상황: 정한 시간 안에 체결되지 않거나 일부만 체결된다.
보이는 것: 체결된 만큼만 보유로 보인다.
시스템 처리: 남은 주문을 취소하고 이유를 남긴다.
출처: [F3](spec.md#f3) › 예외 흐름 › 4c. 정한 시간 안에 하나도 체결되지 않는다

### <a id="e13"></a>E13 증권사 주문 실패

상황: 증권사가 주문을 받지 않거나 응답하지 않는다.
보이는 것: 이상 상황 알림이 온다.
시스템 처리: 이상 감지 멈춤으로 바꾸고 새 주문을 멈춘다.
출처: [F3](spec.md#f3) › 예외 흐름 › 4d. 증권사 주문이 실패한다

### <a id="e14"></a>E14 자료 가져오기 실패

상황: 자료 출처가 응답하지 않거나 시세가 늦는다.
보이는 것: 가져오지 못한 자료와 이유가 보인다.
시스템 처리: 이상 감지 멈춤으로 바꾸고 그 판단은 하지 않는다.
출처: [F2](spec.md#f2) › 대안 흐름 › 2a. 자료와 연결이 정상인가: 아니오

### <a id="e15"></a>E15 백업 실패

상황: 스냅샷을 암호화하거나 올리지 못한다.
보이는 것: 하루 정리에 백업 실패가 보이고 알림이 온다.
시스템 처리: 다음 장 마감 뒤에 다시 올린다.
출처: [F9](spec.md#f9) › 예외 흐름 › 3a. 백업을 올리지 못한다

### <a id="e16"></a>E16 꺼졌다 다시 켜짐

상황: 팀이 도는 컴퓨터가 꺼졌다가 다시 켜진다.
보이는 것: 사무실 화면에 다시 켜졌다는 표시와 이어서 하는 일이 보인다.
시스템 처리: 저장된 상태에서 이어서 하고, 내던 주문은 증권사와 맞춰 본 뒤에만 새 주문을 낸다.
출처: [F1](spec.md#f1) › 예외 흐름 › 1b. 컴퓨터가 꺼졌다가 다시 켜진다

### <a id="e17"></a>E17 복기 못 끝냄

상황: 복기 담당이 그날 복기를 끝내지 못한다.
보이는 것: 하루 정리에 복기가 남았다고 보인다.
시스템 처리: 못 끝낸 매매를 다음 장 마감 뒤 복기로 넘긴다.
출처: [F5](spec.md#f5) › 예외 흐름 › 2a. 복기 담당이 복기를 끝내지 못한다

### <a id="e18"></a>E18 장 밖 주문

상황: 장이 열려 있지 않을 때 주문 안이 만들어진다.
보이는 것: 장이 열리면 다시 본다는 표시가 보인다.
시스템 처리: 주문 직전 점검에서 막고 다음 장 시작 때 팀장이 다시 판단한다.
출처: 조건표 › 장이 열려 있는가

### <a id="e19"></a>E19 쉬는 날 지시

상황: 오늘 판단이 쉬기인데 사는 계기가 생긴다.
보이는 것: 오늘은 쉬는 날이라는 이유가 보인다.
시스템 처리: 새로 사지 않고 보유 종목의 손절과 청산만 한다.
출처: 조건표 › 오늘 판단

### <a id="e20"></a>E20 판단 없이 주문

상황: 종목 판단이 사기나 팔기로 남지 않은 주문 안이 온다.
보이는 것: 막힌 이유가 보인다.
시스템 처리: 판단됨 상태가 아닌 매매의 주문은 받지 않는다.
출처: 조건표 › 종목 판단

### <a id="e21"></a>E21 한도 넘는 주문

상황: 주문 금액이 자동 주문 금액 한도를 넘는다.
보이는 것: 승인 요청 알림이 온다.
시스템 처리: 승인대기로 두고 승인되기 전에는 주문하지 않는다.
출처: 조건표 › 금액 한도 안인가

### <a id="e22"></a>E22 답 없음

상황: 승인 요청에 정한 시간 동안 답이 없다.

### <a id="e46"></a>E46 공지로 규칙 · 승인을 바꾸려 함 (안내 글은 아직 만들지 않음 — backlog)

### <a id="e52"></a>E52 하루 AI 호출이 상한에 가까움 (아직 만들지 않음 — backlog)

시스템 처리: 정리 모드에서는 새 자료 가져오기와 더 말하기를 멈추고 지금까지로 의견을 내게 한다. 팀장 예비분은 다른 담당이 쓰지 않는다. 손절 · 청산은 규칙 엔진이 하므로 상한과 상관없이 계속된다(P2 · P11). 상한을 다 쓰면 지금처럼 그날 논의 · 깨우기를 쉬고 알린다.

### <a id="e53"></a>E53 근거 카드 빈 칸 (아직 만들지 않음 — backlog)

상황: 의견 칸이 비었거나, 칸이 생기기 전 매매다.
보이는 것: 빈 칸은 "없음", 옛 매매는 "기록 없음", 기권은 0점과 다른 "기권"으로 보인다.
시스템 처리: 빈 칸을 추정해 채우지 않는다.
출처: [F7](spec.md#f7) › 기본 흐름 › 7

### <a id="e54"></a>E54 정산할 시세가 없음 (아직 만들지 않음 — backlog)

상황: 정산 날 종가를 받을 수 없다(거래정지 · 자료 오류).
보이는 것: 그 메모는 정산 대기로 남고, 정산 날에서 [N20](#n20)의 날수가 더 지나면 "정산 못 함(시세 없음)"이 된다.
시스템 처리: 정산 날까지 확정된 시세만 쓰고 판단 시각 뒤 자료로 앞을 채우지 않는다(P10).
출처: [F5](spec.md#f5) › 기본 흐름 › 0-2

### <a id="e55"></a>E55 오래된 "일하는 중" (아직 만들지 않음 — backlog)

상황: 담당의 "일하는 중"이 300초 동안 새 소식 없이 남아 있거나, 늦게 온 옛 상태 이벤트가 있다.
보이는 것: 300초가 지나면 쉼으로 보인다. 옛 이벤트는 표시를 바꾸지 않는다.
시스템 처리: 상태 이벤트마다 단조 증가 시각을 붙이고 이미 본 것보다 옛 것은 버린다. 해제는 기록에 남긴다.
출처: [F7](spec.md#f7) › 예외 흐름 › 2a

### <a id="e56"></a>E56 시연 달력이 실제로 새어 나감

상황: 실제 모드에서 시연 달력을 쓰려 하거나, 시연 모드에서 실제 증권사 · AI를 부르려 한다.
보이는 것: 없다(일어나면 안 된다).
시스템 처리: 시연 달력은 시연 어댑터 안에만 있고 실제 모드는 시장 어댑터 달력만 쓴다. 시연 모드는 모의계좌와 가짜 AI만 쓰고 바깥으로 나가는 요청을 만들지 않는다.
출처: [F1](spec.md#f1) › 대안 흐름 › 1c

### <a id="e57"></a>E57 관리 화면 값을 못 받음

상황: 관리 화면이 서버에서 값을 받지 못한다(연결 끊김 · 서버 오류).
보이는 것: 그 칸에 "불러오지 못함 · 다시 시도"가 보이고 메뉴와 다른 칸은 그대로 쓴다.
시스템 처리: 실패한 요청만 다시 보낼 수 있게 하고, 받은 적 있는 값은 "마지막으로 받은 값"으로 함께 보인다.
출처: [F12](spec.md#f12) › 예외 흐름 › 1a

### <a id="e58"></a>E58 화면에서 실전 운용 시작

상황: 템플릿 화면에서 "실전 운용 시작"을 누른다.
보이는 것: 승격대기가 아니면 단추가 막히고 모자란 기준이 보인다. 승격대기면 승인 요청이 생기고 "이 판에서는 실전 주문이 나가지 않는다"가 함께 보인다.
시스템 처리: 승격은 상태 · 승인까지만 잇고 실전 주문은 언제나 [E25](#e25)로 막는다(AGENTS 6번, 결정 2026-11-21 6번). 전체 정지 중에는 승격을 막는다.
출처: [F12](spec.md#f12) › 대안 흐름 › 2b

### <a id="e59"></a>E59 두 화면에서 내 캐릭터

상황: 컴퓨터에서 사무실 화면을 두 개 연다.
보이는 것: 각 화면에서 내 캐릭터가 따로 움직인다. 다시 열면 마지막으로 저장된 자리에서 시작한다.
시스템 처리: 마지막에 온 자리 저장이 이긴다. 다른 화면에 내 위치를 중계하지 않는다.
출처: [F10](spec.md#f10) › 기본 흐름 › 1

### <a id="e60"></a>E60 연출이 겹치거나 화면이 숨음 (아직 만들지 않음 — backlog)

상황: 익절 · 손절이 잇따라 나거나 탭이 숨은 동안 난다.
보이는 것: 연출이 차례로 보인다. 숨은 동안 난 것은 건너뛰고 채팅 · 히스토리에는 남는다.
시스템 처리: 연출은 화면만의 일이고 매매 기록과 상관없다.
출처: [F4](spec.md#f4) › 기본 흐름 › 6-1

### <a id="e61"></a>E61 이미 전체 정지

상황: 전체 정지 중에 다시 "전체 정지"를 누르거나 메신저로 `/stop`을 보낸다.
보이는 것: 계좌 화면에는 정지 단추 대신 "다시 시작"만 보이고, 메신저는 이미 정지라고 답한다.
시스템 처리: 409 `already_stopped`로 답하고 팀 상태와 기록을 바꾸지 않는다.
출처: [F12](spec.md#f12) › 대안 흐름 › 5b

### <a id="e62"></a>E62 끌 수 없는 알림을 모두 끔

상황: 승인 요청 · 전체 정지와 이상 감지 멈춤 · 손절 알림의 폰과 메신저 전달처를 둘 다 끄려 한다.
보이는 것: 저장되지 않고 오류 줄이 보인다.
시스템 처리: 400으로 거절하고 설정을 바꾸지 않는다. 설정 파일을 읽지 못하면 기본(모두 보냄)으로 보내 알림이 조용히 사라지지 않게 한다.
출처: [F12](spec.md#f12) › 대안 흐름 › 6b

### <a id="e63"></a>E63 다른 프로그램이 서버 자리를 차지함

상황: `price-inha setup` · `access-key` · `open`이 찾은 포트에서 답하는 것이 이 보관 폴더의 서버가 아니다(실행 증표가 맞지 않거나, 증표 파일이 없거나, 파일의 주인 · 권한이 이상하다).
보이는 것: "이 포트에서 답하는 것은 이 보관 폴더의 서버가 아닙니다"로 멈춘다.
시스템 처리: 비밀값 · 주소를 보내지 않고 끝낸다([N23](#n23)).
출처: [R19-2](prd.md#r19-2)

### <a id="e64"></a>E64 메신저 토큰 거절 · 페어링 코드 틀림

상황: 등록하려는 봇 토큰을 텔레그램이 거절하거나, 넣은 페어링 코드가 맞지 않는다.
보이는 것: 토큰은 저장되지 않았다는 안내가, 코드는 "코드가 맞지 않습니다"가 보인다. 5번 틀리면 1시간 잠기고 풀리는 시각이 보인다. 받는 중에 토큰이 거절되면 상태가 "토큰 거절"로 바뀌고 알림이 한 번 간다.
시스템 처리: 확인에 실패한 토큰은 저장하지 않고, 남은 횟수는 알려 주지 않는다.
출처: [F12](spec.md#f12) › 대안 흐름 › 6c

CLI(`setup` · `access-key` · `open`)는 비밀값을 보내기 전에 `POST /api/whoami` `{"nonce"}`로 받은 요약값(증표 · nonce · 자기가 접속한 포트로 만든 SHA-256)을 대조하고, 맞지 않으면 멈춘다([E63](#e63)). 서버는 같은 컴퓨터에만 답하고, 자기가 실제로 연 포트로 계산하며, 비교는 상수 시간이다. 증표는 기록 · 응답 · 이벤트 어디에도 나오지 않는다. 출처: server 38차, `docs/research/remote-access-security.md`
- <a id="n24"></a>N24 메신저는 텔레그램 하나이고(결정 26) long polling만 쓴다(밖에서 들어오는 포트가 없다). 페어링 코드는 8자리 · 1시간 · 대기 3건, 허용은 한 사람, 1:1 대화만 받는다. 나가는 글은 가린 글만 보내고 가리기에 실패하면 보내지 않는다. 보내기 실패는 팀의 일을 막지 않는다(물러서며 3번까지). 시연 모드는 메신저를 돌리지 않는다. 출처: 결정 24 · 26, `docs/research/onboarding-messenger.md` 2.4~2.6
- <a id="n25"></a>N25 알림 설정과 알림음은 서버의 홈 폴더 설정 파일에 둔다(브라우저 저장소에 두지 않는다 — 결정 22). 알림 기본은 모든 종류 켜짐 · 조용한 시간 꺼짐, 알림음 기본은 켜짐이다. 조용한 시간은 시장 시간대의 시각이고 자정을 넘는 구간을 받으며, 급한 알림(승인 요청 · 멈춤 등)은 조용한 시간에도 간다. 설정을 읽지 못하면 모두 보낸다. 출처: server 31차 고침 · 40차, 결정 22
