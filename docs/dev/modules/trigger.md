# trigger 모듈 (T11, T13의 일정)

크레이트 `pi-trigger`, 폴더 `crates/trigger/`. 구성 요소 A5. `pi-market`(달력 · 시세)을 쓴다. 영수증 저장과 깨울 대상은 포트(trait)로 받는다(조립에서 store 10차 · agent를 끼운다). 시각은 Clock으로 받는다.
근거: `dev.md` N6 · E16 · E18 · E14, `spec.md` F1 · F2.

## 원본 동작 근거

- tick 순서(잠금 → 전체 정지 확인 → 다시 읽기 → 기한 판정 → 먼저 옮기고 발사), 유예 = 주기 절반, 놓친 회차는 한 번만: `docs/research/triggers-approval-memory-deep.md` 1.1, `docs/research/hermes-agent.md` 6.1.
- 영수증 `(작업, 예정 시각)`과 실행 중은 하나, 다시 켜면 실행 중이던 것은 중단됨으로 닫고 다시 돌리지 않음, 오류 지연 30초 · 60초 · 5분 · 15분 · 60분과 10번이면 끔, 60초 상한 타이머와 벽시계 · 단조 시계 비교, 대기열(대상마다 20 + 20, 키 중복 · 교체 · 합치기): `docs/research/triggers-approval-memory-deep.md` 1.2 · 2.2 "가격인하에 옮길 때", `docs/research/openclaw.md` 2.1 · 4의 1~4번.
- 원본에 없어 새로 정한 것: 장 시간 밖 따라잡기, 시세 조건 다시 걸기, 휴장일(결정 2026-11-16 20 · 21번).

## 만드는 것 (1차)

1. 일정: 장 시작 전 브리핑, 장 시작, 장 마감, 마감 뒤(복기 · 백업). 시각은 시장 달력에서 낸다(KR · US).
2. 시세 조건(넘음 · 내려감 · 변동률)과 다시 걸기 간격(알린 값에서 반대로 0.5% 벗어났다가 돌아오면 다시 건다, 설정 값), 시세 늦음 감시(N6 30초 → 이상 깨움).
3. 영수증과 다시 켠 뒤 처리(E16), 놓친 것 처리. 장 밖이면 따라잡지 않고 다음 장 시작 하나로 합친다(E18).
4. 실패하면 물러서고, 10번이면 끄고 알림 요구를 낸다.
5. `Waker` 포트에 대상(팀 · 담당)과 이유, 묶인 사건들을 넘긴다.

## 2차 작업 (1차 검토 되돌림 — 2026-11-16)

1. **저장소 쓰기가 중간에 실패해도 회차를 잃지 않는다**: 작업마다 "상태 옮기기 + 영수증 열기"를 한 단위로 묶는다(포트에 한 번에 하는 메서드를 둔다). 한 작업이 실패하면 그 작업만 이번 발사에서 빠지고(상태 그대로) 나머지는 깨운다. 이번 tick에 연 영수증은 깨우지 못했으면 닫는다(실패로). 영수증이 실행 중으로 남아 그 작업이 영영 막히는 일이 없다. N번째 쓰기부터 실패하는 가짜 저장소로 확인한다.
2. **tick은 실행이 끝날 때까지 잠금을 쥐지 않는다**: 깨우기는 띄워 두고(대상마다 따로) tick 잠금을 바로 놓는다. 결과가 오면 영수증을 닫는다. 실행 중 영수증이 중복 울타리다(원본 Hermes 1.1 12·13단계, OpenClaw). 오래 걸리는 깨우기가 도는 동안에도 늦은 시세 감시(N6 30초)·시세 조건·60초 시계 확인이 계속된다.
3. 다시 켤 때: 상태를 옮겼는데 영수증이 없는 회차는 되살린다(원본 Hermes의 주인 없는 대기 회차).

## 3차 작업 (2차 검토의 참고 — server 조립 전에 한다)

1. 띄운 깨우기가 패닉해도 영수증을 실패로 닫고 `in_flight`를 줄인다(패닉하는 가짜 깨우기로 시험).
2. 끝난 결과(`finished` · `errors`)를 기다리지 않고 가져가는 길을 두고, `run()`이 그것으로 비운다(끝없이 쌓이지 않음).
3. tick이 중간에 빠져도 꺼낸 되살릴 회차를 잃지 않는다(달력이 없을 때 포함).
4. 같은 작업이 실행 중이라 기한으로 남은 회차 때문에 2초마다 tick이 돌지 않게, 실행 중인 작업의 회차는 다음 대기 계산에서 뺀다.
5. 되살린 회차가 발사되면 `pending_slot`을 지운다(영수증 정리가 생겨도 옛 회차를 되살리지 않게).
6. 시세를 받는 동안에는 쓰기 잠금을 쥐지 않는다.

## 4차 후보 (3차 검토의 참고 — 아직 시작하지 않음)

1. 바깥 작업 안에서 저장소가 패닉해도 `leave`가 불리게 drop guard로(지금은 그 작업이 실행 중으로 굳는다).
2. `settle()` future가 취소돼도 꺼낸 핸들을 잃지 않게.
3. 일반 발사의 `pending_slot` 정리(영수증 정리 기능이 생길 때).

## 5차 작업 (후보 일괄 처리)

4차 후보 1~3번을 했다.

1. 띄운 바깥 작업이 어떻게 끝나든(저장소 패닉 포함) drop guard가 `in_flight`를 줄이고 작업의 실행 중 표시를 푼다.
2. `settle()`은 핸들을 꺼내 쥐지 않고 끝난 수가 0이 되기를 기다린다(알림 기반). future가 취소돼도 깨우기를 잃지 않고 다음 `settle`이 끝까지 기다린다.
3. 깨우기가 끝나 영수증을 닫을 때 그 회차의 `pending_slot`을 지운다(성공 · 실패 모두). 영수증 정리 기능은 아직 없지만, 생겨도 옛 회차를 되살리지 않는다.

## 하지 않는 것

판단, 저장소 직접 쓰기, 바깥 HTTP 입구(webhook).

## 테스트 주의

가짜 시계와 가짜 달력으로 시간을 건너뛴다(실제로 잠들지 않는다). 시계가 뒤로 가거나 절전에서 깬 경우를 시험한다.
