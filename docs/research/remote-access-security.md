## 1. 결론

사용자가 정한 것(사실): 원격 접속은 Tailscale, VPN 모드는 사용자가 **수동으로** 켜고 끄며 끄면 인터넷 어디서나 접속, 앱 안 2차 인증은 두 모드 모두 TOTP, VPN을 끈 상태에서는 키 같은 민감한 화면 · 기능을 막음, OTP를 잃으면 서버 컴퓨터 앞에서 초기화, 백업은 private GitHub에 암호화(동작 상태 · 템플릿 · 지식 DB 포함, 비밀 제외), 보안 요구사항은 기획에 넣음.

[추정] 이를 구현하는 기본안:

1. **입구**: 서버(에이전트 실행기 + 사무실 서버)는 언제나 `127.0.0.1`에만 열고, 밖으로 나가는 길은 Tailscale 하나다. VPN 모드에서는 `tailscale serve`로 내 tailnet에만 HTTPS(`기기이름.tailnet이름.ts.net`, Let's Encrypt 자동)를 열고, ACL `autogroup:self` · 기기 승인 · 키 만료 · tailnet lock을 켠다.
2. **VPN 끈 모드**: 같은 443을 `tailscale funnel`로 바꿔 인터넷에 연다. 주소가 그대로라 폰 PWA와 웹 푸시가 끊기지 않는다. 끄기는 VPN 모드 안에서 새 TOTP로만, 켜기는 어디서나 바로. 자동 복귀는 없고, 끈 상태가 이어지면 알림에 "VPN 켜기" 버튼을 준다. 끈 상태에서는 토스 키 · AI 키 · OAuth 화면과 API, TOTP 재설정, 기기 추가, 위험을 키우는 규칙 변경 · 실전 승격 · 킬 스위치 재개를 막는다.
3. **로그인**: VPN 모드는 tailnet 기기 + TOTP, 끈 모드는 비밀번호 + TOTP. 세션은 서버 저장형으로 짧게, 시도 제한과 알림을 둔다. Tailscale 계정이 뚫려도 TOTP가 두 번째 벽이다.
4. **승인**: 한도 넘는 주문 등 위험을 키우는 승인은 건마다 새 TOTP 코드로 확인하고, 같은 코드 재사용 · 같은 승인 재전송 · 승인 뒤 내용 바꿔치기를 막는다. 검증 실패는 언제나 거절이며 "답 없음 → AI 판단" 경로로 새지 않는다. 거절 · 멈춤은 바로 된다.
5. **비밀**: 토스 키는 주문 노드 하나의 OS 키체인에만, AI · 로그 · 화면 · 푸시 · API 응답에 나오지 않게 한다.
6. **OTP 분실**: 서버 컴퓨터 앞에서 명령 하나로 초기화하고 새 폰에 다시 등록한다. 메일 · 구글 복구는 없다.
7. **백업**: 매일 장 마감 뒤 DB를 일관된 스냅샷으로 떠서 `age`로 암호화해 private GitHub에 올린다. 서버에는 공개키만, 푸는 열쇠는 GitHub 밖에 둔다. 복원하면 승인 대기는 모두 만료, 증권사 잔고와 맞출 때까지 신규 주문 정지, 키와 TOTP는 직접 다시 등록한다.

### 2.3 어디가 뚫리나 [추정]

1. **입구**: 서버가 `0.0.0.0`에 뜨거나, 끈 모드가 잊힌 채 계속 공개되는 것.
2. **인증**: 약한 비밀번호, 시도 제한 없음, 긴 세션(예: 7일 JWT, 폐기 불가), 개발용 고정 서명키.
3. **승인 경로**: 세션 쿠키만으로 승인 통과, 같은 승인 재전송, 승인 뒤 내용 바꿔치기.
4. **비밀 저장**: 평문 `.env`, 로그 · 오류 · 화면 · API 응답에 키 노출, 에이전트 도구가 키를 읽음.
5. **복구 경로**: 이메일 · 계정 기반 복구가 가장 약한 고리가 되는 것.
6. **노드 사이**: 집 PC · 노트북 · 미니 PC · VPS 사이 내부 API가 인증 없이 열림.

## 3. 원격 접속 방식 비교 (짧게)

| 방식 | 공격면 | 비용 | PWA · 웹 푸시 | 판정 [추정] |
|---|---|---|---|---|
| **Tailscale + Serve** | 가장 작음(공개 포트 없음, tailnet 기기만) | 개인 무료 | `*.ts.net` HTTPS 자동 | **VPN 모드(기본)** |
| **Tailscale Funnel** | 공개(443 · 8443 · 10000). 중계 서버는 복호화 안 함 | 무료, 베타 | Serve와 같은 주소 → PWA · 푸시 그대로 | **끈 모드 1순위** |
| Cloudflare Tunnel (+Access) | 공개 도메인, 들어오는 포트 없음. TLS가 Cloudflare 엣지에서 풀림 | 무료(Access 50명 미만), 도메인 필요 | 다른 주소 → PWA 다시 설치 · 푸시 다시 구독 | 끈 모드 2순위 |
| 공유기 포트 포워딩 / VPS 리버스 프록시 | 가장 큼(내 IP · 서버가 직접 노출) | 무료 / VPS 비용, 도메인 · 인증서 직접 | 다른 주소 | 버림 |
| WireGuard 직접 · Headscale | 작음, 대신 운영 부담 큼 | 무료(+서버) | 인증서 따로 | 버림 / 나중 |

근거 [사실]:

- Serve는 tailnet 안에서만 공유, Funnel은 인터넷 공개. 같은 포트를 Serve와 Funnel에 동시에 쓸 수 없고 마지막 명령이 funnel이면 그 포트는 완전히 공개. https://tailscale.com/docs/features/tailscale-serve.md
- Funnel: 포트 443 · 8443 · 10000만, 기본 꺼짐, 베타, 정책 파일 `nodeAttrs`의 `funnel` 필요, 대역폭 제한(설정 불가), Tailscale CLI가 도는 플랫폼에서만, macOS는 특정 앱 변형만. 중계 서버는 트래픽을 복호화하지 않는다. 공개 DNS 반영에 최대 10분. https://tailscale.com/docs/features/tailscale-funnel.md
- Cloudflare Access 무료는 50명 미만 팀용 https://www.cloudflare.com/en-au/products/cloudflare-access , cloudflared는 밖으로만 연결 https://www.cloudflare.com/products/argo-tunnel , 엣지 TLS 종료는 2차 출처만 https://flaviocopes.com/cloudflare-tunnel/
- Headscale은 Tailscale 제어 서버의 오픈소스 구현, tailnet 하나만. https://wz-it.com/en/knowledge/remote-access/what-is-headscale/

### 4.2 VPN 모드 토글 (켜면 tailnet만, 끄면 인터넷 어디서나)

**구조 [추정]**: 서버 바인딩은 두 모드 모두 `127.0.0.1` 그대로이고, 바뀌는 것은 Tailscale이 443을 `serve`(tailnet만)로 여느냐 `funnel`(공개)로 여느냐뿐이다. 바인딩 주소를 바꾸지 않아도 되고, 주소(origin)가 같아 PWA · 푸시 구독 · 쿠키가 그대로다.

앱이 모드를 스스로도 강제한다:

- VPN 모드에서는 Serve가 넣는 신원 헤더(`Tailscale-User-Login`)가 있고 그 값이 내 계정일 때만 받는다. Funnel 트래픽에는 신원 헤더가 없으므로 [사실, Serve 문서] Funnel이 실수로 켜져 있어도 앱이 거부한다.
- 끈 모드에서도 tailnet 안 기기는 신원 헤더가 붙어 오므로 앱은 "tailnet에서 옴 / 공개에서 옴"을 구분해 기록하고 권한을 다르게 줄 수 있다(OpenClaw 문서도 Funnel 주소의 tailnet 동료는 Serve 신원 경로로 간다고 적음, `docs/gateway/tailscale.md:83-84` [관찰]).
- loopback으로 들어오는 헤더는 같은 호스트 프로세스가 위조할 수 있다. 서버 호스트는 믿는다는 가정이며, 그래서 신원 헤더는 TOTP를 대신하지 않는다.

### 4.3 TOTP 설계

**첫 등록**

1. 처음 설정은 서버 앞(loopback) 또는 VPN 모드에서만. 끈 모드에서는 등록 화면을 열지 않는다.
2. 서버가 160비트 랜덤 비밀값을 만든다(RFC 4226 권장 길이 [사실] https://www.rfc-editor.org/rfc/rfc4226.txt). `otpauth://` QR을 **한 번만** 보여 주고, 인증 앱에서 나온 코드를 한 번 맞혀야 등록 완료.
3. 서버 저장: TOTP는 서버도 같은 비밀값을 가져야 검증할 수 있다(대칭). 그래서 DB에는 AES-256-GCM으로 암호화해 두고, 암호화 키는 DB가 아닌 OS 키체인에 둔다(6장). 화면 · API로 다시 꺼내는 경로는 없다. RFC 6238도 검증 시스템에 키를 안전하게 저장하라고 권한다 [사실] https://www.rfc-editor.org/rfc/rfc6238.txt
4. (선택) 복구 코드를 쓰기로 하면 같은 화면에서 발급(4.4).

**검증 규칙**

| 규칙 | 값 | 근거 |
|---|---|---|
| 시간 단위 | 30초, 6자리 | RFC 6238 기본 권장 30초 [사실] |
| 시간 오차 허용 | 현재 ±1단계(최대 약 90초 창) [추정] | RFC 6238은 전송 지연용으로 이전 단계 최대 1개 허용을 권함 [사실]. 서버 시계는 NTP로 맞춤 |
| 같은 코드 재사용 | 마지막으로 받은 시간 단계를 저장하고 **그 단계 이하는 거부** | RFC 6238: 성공한 같은 OTP의 두 번째 시도를 받으면 안 됨 [사실]. NIST: 유효 기간 안에 한 번만 [사실] https://pages.nist.gov/800-63-4/sp800-63b/authenticators |
| 시도 제한 | 4.6 | RFC 4226은 서버 쪽 시도 제한 · 잠금을 권함 [사실] |
| 피싱 | TOTP는 피싱에 강하지 않다(가짜 화면이 6자리를 실시간 중계 가능) | NIST [사실] 같은 페이지 |

**언제 묻나 [추정]**

| 때 | VPN 모드 | 끈 모드 |
|---|---|---|
| 로그인 | TOTP | 비밀번호 + TOTP |
| 한도 넘는 주문 승인 · 위험을 키우는 규칙 변경 · 실전 승격 · 킬 스위치 재개 | 건마다 새 코드 | 주문 승인만 건마다 새 코드, 나머지는 불가 |
| VPN 모드 끄기 · 비밀키 등록 · 기기 추가 · 복구 코드 재발급 | 새 코드 | 불가 |
| 거절 · 멈춤 · 킬 스위치 켜기 · VPN 모드 켜기 · 세션 끊기 | 묻지 않음 | 묻지 않음 |

한 30초 안에 승인 두 건을 하면 두 번째는 다음 코드를 기다린다(재사용 금지의 결과).

**패스키(WebAuthn)와 비교**

| 점 | TOTP | 패스키 |
|---|---|---|
| 피싱 저항 | 없음 | 있음(도메인에 묶임) |
| 폰 하나로 승인할 때 | 인증 앱으로 넘어가 6자리 복사 · 입력 | Face ID 한 번 |
| PWA 지원 | 입력칸만 있으면 됨, 어디서나 | iOS · 안드로이드 최신 브라우저에서 됨, 홈 화면 PWA 동작은 기기마다 확인 필요 |
| 승인 내용에 묶기 | 코드가 내용과 무관 → 서버 쪽 1회용 · 짧은 만료로 보완 | 서버 challenge를 승인 건에 묶어 서명 |
| 서버가 털리면 | 비밀값이 서버에 있음 → 암호화 필수 | 서버에는 공개키만 |
| 구현 난이도 | 낮음 | 중간(Rust `webauthn-rs`, 의식 상태 서버 저장 필요 [사실] https://docs.rs/webauthn-rs/) |

| 주소가 바뀔 때 | 무관 | 등록한 도메인(rpId)에 묶임 → Cloudflare 등 다른 주소로 가면 다시 등록 |

[추정] 지금은 사용자 결정대로 TOTP로 간다. 피싱에 약한 점은 (1) 끈 모드를 짧게 · 알림으로 관리, (2) 공개 경로에서 관리 기능을 막는 것으로 줄인다. 나중에 패스키를 "TOTP 대신 쓸 수 있는 선택지"로 더하면 승인이 더 편하고 피싱에도 강해진다.

### 4.4 TOTP 분실 · 복구

| 방식 | 공격 경로 | 1인 홈서버에 맞나 | 구현 |
|---|---|---|---|
| (a) 이메일 · 구글 계정 로그인으로 복구 | 구글 · 메일 계정 하나가 뚫리면 TOTP도 뚫림. Tailscale 로그인도 같은 구글 계정이면 **망과 2차 인증이 한 번에** 넘어감. 서버에 메일 발송 비밀(SMTP 키 등)이 하나 더 생김 | 안 맞음 | 중 |
| (b) 처음 등록 때 받는 1회용 복구 코드 | 코드를 적어 둔 종이 · 비밀번호 관리자가 털리면 뚫림. 서버에는 해시만, 쓰면 폐기 | 맞음 | 낮음 |
| (c) 서버가 도는 컴퓨터에서 직접 초기화(로컬 콘솔 명령) | 그 컴퓨터에 물리 접근 · 관리자 권한이 있어야 함 → 이미 다 뚫린 상태와 같아 새 위험이 거의 없음. 대신 밖에서는 못 함 | 맞음(최후 수단) | 낮음 |
| (d) 인증 앱 백업(구글 OTP 클라우드 동기화 · 내보내기 QR)으로 새 폰에 옮기기 | 클라우드 동기화를 켜면 TOTP 비밀값이 구글 계정에 묶임 → (a)와 같은 연쇄 위험. 내보내기 QR(옛 폰 → 새 폰)은 옛 폰이 있어야 함 | 사용자 선택 | 앱 기능(서버 구현 없음) |

[사실] 구글 OTP 앱은 클라우드 동기화(구글 계정 로그인)와 수동 내보내기 QR 두 가지로 새 폰에 옮길 수 있고, 클라우드 동기화는 켜야만 동작한다. https://support.google.com/accounts/answer/1066447 (세부는 2차 출처 https://engadget.com/2307835/how-to-set-up-google-authenticator-new-phone )

**결정 · 추천**: 사용자가 **(c) 서버 컴퓨터 앞에서 명령 하나로 초기화**로 정했다. (a)는 쓰지 않는다. [추정] 구현: `가격인하 otp-reset` 같은 로컬 명령이 (1) 그 컴퓨터의 관리자 권한과 대화형 터미널에서만 돌고(네트워크 API로는 부를 수 없음), (2) 옛 TOTP 비밀값과 모든 세션을 지우고, (3) 새 QR을 그 화면에만 띄워 등록받고, (4) 모든 기기에 "TOTP가 초기화됨" 알림과 접속 기록을 남긴다. (b) 복구 코드는 밖에서 급히 복구할 수단이 없다는 약점을 메우는 선택지로만 남긴다(넣을지는 사람이 정함). (d) 클라우드 동기화는 구글 계정과 묶이므로 쓰지 말고, 폰 교체는 옛 폰에서 내보내기 QR로 옮기기를 권한다.

[추정] 이 방식의 대가: 밖에 있을 때 폰을 잃으면 집(또는 그 서버 컴퓨터)에 갈 때까지 로그인 · 승인을 못 한다. 그동안 승인은 "답 없음" 규칙(FN2 3b)으로 처리된다. VPS가 주 서버면 "서버 컴퓨터 앞"은 VPS 콘솔(클라우드 업체 웹 콘솔 · SSH)이 되므로, 그 클라우드 계정 보안이 곧 TOTP 복구 보안이 된다.

**폰을 잃어버렸을 때 [추정]**

1. 다른 기기(노트북)에서 바로 VPN 모드 켜기(끈 상태였다면) → 기기 목록에서 잃어버린 폰의 세션 모두 끊기.
2. Tailscale 관리 콘솔에서 그 폰을 tailnet에서 제거(tailnet lock이 있으면 서명도 폐기).
3. 인증 앱이 그 폰에만 있었다면: 서버 컴퓨터 앞에서 `otp-reset` 명령으로 초기화 → 새 폰 인증 앱에 다시 등록(옛 비밀값 무효).
4. 끈 모드 예약이 걸려 있으면 취소.

| 서버 재시작 | 세션 유지 여부는 사람이 정함. NIST는 세션 비밀을 재시작 너머로 남기지 말라고 권함 [사실] https://pages.nist.gov/800-63-4/sp800-63b/session | 24시간 운용 + 재시작(F1 예외 1b)과 충돌 |
| 폐기 | 기기별 끊기, "모든 세션 끊기" | 분실 대응 |
| CSRF · 소켓 | SameSite=Strict + `Origin` 검사, WebSocket도 같은 쿠키 · `Origin`, 세션 폐기 시 소켓도 끊음 | DeskRPG 소켓은 쿠키 JWT만 봄 |

### 4.6 시도 제한 · 잠금 [추정]

- 비밀번호 · TOTP · 복구 코드 실패를 경로(tailnet/공개)별 · IP별로 센다. 출발점은 OpenClaw 기본값 "60초에 10번 실패 → 그 IP 5분 잠금"(`docs/gateway/security/rate-limiting.md` [관찰]). 공개 경로는 더 엄격하게: TOTP 5번 실패마다 지연을 두 배로, 10분에 20번이면 공개 경로 로그인을 30분 막고 알림(VPN 경로는 그대로).
- 6자리에 ±1단계 창이면 한 번 찍어 맞힐 확률이 약 3/1,000,000이라, 시도 제한이 TOTP 강도의 핵심이다.
- 1명용이라 계정 전체 잠금은 하지 않는다(공격자가 나를 못 들어오게 만드는 것 방지). 대신 VPN 경로는 공개 경로 실패와 별도 카운터로 둔다.
- Serve · Funnel은 loopback으로 프록시하므로 OpenClaw식 "loopback 실패 예외"를 두면 밖의 시도까지 예외가 된다(OpenClaw `network-exposure.md:200` [관찰]). 예외를 두지 않는다.
- 오류 문구는 하나("인증 실패"). OWASP도 일반 오류를 권한다 [사실, 2차 인용] https://cheatsheetseries.owasp.org/cheatsheets/Passkey_Security_Cheat_Sheet.html
- 실패 폭주 · 새 기기 · 공개 경로 로그인 성공은 폰에 알림.

### 4.7 Tailscale 계정이 뚫렸을 때 · 노드 사이

- [추정] 앱 안 2차 인증(TOTP)은 여전히 필요하다. Tailscale 로그인 계정이 털리면 공격자가 관리자로서 기기를 추가 · 승인할 수 있다(기기 승인은 관리자가 하므로 같은 계정이면 소용없음). tailnet lock을 켜 두면 내 신뢰 노드 서명 없이는 노드가 들어오지 못한다 [사실, tailnet lock 문서]. 그래도 둘 다 뚫린 경우를 위해 앱이 TOTP를 따로 요구한다. Tailscale 로그인 계정과 TOTP 복구를 같은 구글 계정에 묶지 않는 것이 이 판단의 전제다(4.4).
- 노드 사이(에이전트 실행기 ↔ 주문 노드 등)는 tailnet + ACL로 필요한 짝만 열고, 그 위에 역할별 노드 키(16자 이상 랜덤, 상수 시간 비교, 없으면 시작 거부 — Hermes api_server 방식 [관찰])를 둔다. 플러그인처럼 키 하나에 전 권한을 몰지 않는다.

## 5. 주문 승인 보호

### 5.1 승인 한 건의 흐름 [추정]

1. 규칙 엔진(FN1)이 한도를 넘는 주문을 만들면 **승인 요청 레코드**를 만든다: `approval_id`, 종류(주문 / 규칙 변경 / 실전 승격 / 재개), 내용(종목 · 방향 · 수량 · 가격 상한 · 계좌 별칭 · 금액), 내용 해시, 만료 시각, 상태 `대기`.
2. 폰 · 사무실에 알림(푸시 내용은 최소). 화면은 서버 레코드에서만 그린다.
3. "승인"을 누르면 화면이 `approval_id + 내용 해시 + 새 TOTP 코드`를 보낸다.
4. 서버는 (a) 세션이 유효하고 그 경로(tailnet/공개)에서 이 종류 승인이 허용되는지, (b) 내용 해시가 레코드와 같은지, (c) 만료 전인지, (d) TOTP 코드가 맞고 이전에 받은 시간 단계보다 새것인지를 확인한다.
5. 한 트랜잭션 안에서 `대기 → 승인`으로 **한 번만** 바꾸고 TOTP 마지막 시간 단계를 갱신한다(이미 바뀌었으면 실패).
6. 실행 직전에 시세 · 한도 · 원칙을 다시 확인하고 **저장된 계획만** 실행한다. 승인 뒤 바뀐 인자는 버린다(OpenClaw exec 승인 방식, `docs/tools/exec-approvals.md:739-785` [관찰], [OpenClaw 분석 2.2](openclaw.md)).

### 5.2 무엇을 막나

| 공격 | 막는 장치 |
|---|---|
| 세션 쿠키를 훔쳐 승인 | 승인마다 새 TOTP. 쿠키만으로는 불가 |
| 같은 승인 요청 재전송(리플레이) | TOTP 시간 단계 재사용 거부 + 상태 전이 1회 + `Idempotency-Key`(Hermes `/v1/runs` 방식, [Hermes 분석 5.2](hermes-agent.md)) |
| 승인 뒤 내용 바꿔치기 | 내용 해시 검사 + 실행은 저장된 계획만 |
| 피싱 화면이 6자리를 중계해 다른 건을 승인 | 승인 요청은 서버가 만든 것만 존재, 만료 짧게(예: 10분), 끈 모드에서는 위험을 키우는 승인 불가. TOTP 자체로는 못 막음 → 남는 위험 |
| UI 위조 | 승인 화면은 서버 레코드에서만. AI 문장은 "근거"로 따로 |
| 모르는 결정 값 · 검증 오류 | 전부 거절(OpenClaw: 모르는 결정 = timeout = 거절, hook 실패 = 차단 [관찰]) |

### 5.3 비대칭: 위험을 줄이는 쪽은 쉽게 [추정]

| 행동 | 재인증 |
|---|---|
| 거절, 신규 진입 멈춤, 킬 스위치 켜기, VPN 모드 켜기, 세션 끊기 | 세션만으로 즉시 |
| 한도 넘는 주문 승인 | 건마다 TOTP(두 모드) |
| 위험을 키우는 규칙 변경(P15), 실전 승격(P14), 킬 스위치 뒤 재개(P4) | 건마다 TOTP, VPN 모드에서만 |
| 비밀키 등록 · 교체, 기기 추가, TOTP 재등록, VPN 모드 끄기 | TOTP, VPN 모드(또는 서버 앞)에서만 |

손절 · 청산은 승인 대상이 아니게 두어(P11처럼 손절 · 청산은 허용) 거절 위조로 손절을 막을 수 없게 한다.

### 5.4 답 없음 규칙과의 관계 (FN2 3b)

[관찰] 기획: 답이 없으면 신호마다 템플릿 시간만큼 기다리고, 주문이면 팀이 위험 · 익절 신호를 보고 스스로 판단하며, 사는 주문은 금액 한도 안으로 줄여서 낸다. 재개 · 규칙 개선 · 실전 승격은 내 답이 올 때까지 기다린다([spec FN2](../product/stock-team/spec.md#fn2)).

승인 경로가 뚫리거나 막히면 [추정]:

| 상황 | 결과 | 상한 · 대응 |
|---|---|---|
| 승인 경로가 **막힘**(알림 차단, 폰이 tailnet 밖, 서버 과부하) | 모든 승인이 "답 없음" → AI가 한도 안에서 판단 | 손실 상한은 금액 한도 + P1~P13. 막힘이 감지되면(푸시 실패 · 연결 없음 지속) 더 보수적인 경로(신규 매수 안 함, 손절 · 청산만)로 가는 규칙 후보 |
| 공격자가 **승인을 위조** | 한도 넘는 주문 실행 | 5.1~5.2로 막음. P1~P8은 승인과 무관하게 강제(승인은 금액 한도만 넘게 해 줌) |
| 공격자가 **거절을 위조** | 사야 할 것을 못 삼 | 손해 제한적, 거절 기록에 경로 · 기기 남김 |
| 승인 대기 중 서버 재시작 | — | 승인 요청은 "답 없음" 경로로, 재시작 때 모드 처리는 4.2 |
| 검증 오류 · 알 수 없는 결정 · TOTP 실패 | — | 언제나 거절. **검증 실패를 "답 없음"으로 바꾸지 않는다** |
| 프롬프트 주입으로 AI가 "사용자가 승인했다"고 말함 | — | 승인 정본은 서버 레코드뿐 |

## 6. 비밀 저장과 노출 방지

### 6.1 어디에 두나 [추정]

| 비밀 | 위치 | 비고 |
|---|---|---|
| 토스증권 client_id/secret | **주문 노드 하나**의 OS 키체인 | 다른 노드는 주문 노드 내부 API로 요청. 고정 IP(VPS 등)가 허용 IP와 맞음 |
| AI API 키 · 구독 OAuth 토큰 | 에이전트 실행 노드의 OS 키체인 | 갱신은 Hermes 방식(락 안에서 읽기 · POST · 쓰기) |
| TOTP 비밀값 | DB에 AES-256-GCM 암호문, 암호화 키는 OS 키체인 | DB만 털려서는 못 씀 |
| 비밀번호 · (선택) 복구 코드 | 해시만(Argon2id) | 복구 코드를 쓴다면 1회용 |
| 노드 키 | 각 노드 키체인 | 역할별 |

- OS 키체인: Rust `keyring` 크레이트가 macOS Keychain, Windows Credential Manager, Linux Secret Service(DBus) · keyutils를 한 API로 쓴다 [사실] https://docs.rs/crate/keyring/3.6.3/source/README.md
- [추정] 화면 없는 Linux(VPS · 미니 PC)는 Secret Service가 없을 수 있다. 그때는 저장 시 암호화 파일 + 시작할 때 마스터 비밀번호 또는 systemd 자격 증명으로 대체하고, 파일 0600 · 폴더 0700 · 원자적 교체(Hermes · OpenClaw 공통 [관찰]).

### 6.2 새지 않게 [추정, 원본 관찰 근거]

1. **쓰기 전용**: 등록 후 다시 읽어 주는 경로 없음(플러그인 프로필 키 방식 [관찰]). 화면에는 "등록됨 · 날짜 · 지문"만. 끈 모드에서는 이 화면 · API 자체를 막음.
2. **로그 · 오류**: 비밀 타입을 `Debug`/`Display`에서 가리는 래퍼(예: `secrecy`)로 감싸고, 출력 전 마스킹. 오류에는 예외 타입 이름만(플러그인 [관찰]). Hermes에는 `agent/redact*.py`, OpenClaw에는 로그 내보내기 전 비밀 마스킹(`docs/gateway/logging.md:127-144`) [관찰]. TOTP 코드 · 비밀번호도 로그에 남기지 않음.
3. **에이전트에게 안 보이게**: 도구 프로세스 환경에 키를 넣지 않고, 주문은 규칙 엔진 함수로만. OpenClaw는 작업 폴더 `.env`가 공급자 키를 덮지 못하게 막음(`docs/gateway/security/secrets-and-storage.md:70-80`) [관찰], 플러그인은 산출물 저장에서 `.ssh` · `.aws` · 토큰 폴더를 거름 [관찰].
4. **응답 · 화면 · 푸시**: 직렬화에서 비밀 필드 제외, 푸시 내용 최소화.
5. **백업**: 키체인 내용은 백업에 넣지 않음, 디스크 전체 암호화 권장(OpenClaw 권고 [관찰]).
6. **키 분리**: 세션 서명 · 비밀 암호화 · 노드 인증 · TOTP 암호화에 같은 키를 쓰지 않음. DeskRPG는 `JWT_SECRET` 하나를 세션 서명과 게이트웨이 키 암호화에 같이 씀(`src/lib/gateway-resources.ts:50-80`) [관찰].
7. **자리표시 값 거부**: 빈 값 · `undefined` · 예시 값으로 시작하지 않음(OpenClaw `network-exposure.md:118` [관찰]).

### 6.3 백업 (private GitHub, 암호화)

사용자 결정: 컴퓨터 고장에 대비해 private GitHub 저장소에 암호화해서 올린다. 동작 상태 · 템플릿 · 지식 DB는 모두 포함하고 비밀은 뺀다.

**무엇을 넣고 무엇을 빼나**

| 넣는다 | 빼는다(절대) |
|---|---|
| 동작 상태: 팀 · 에이전트 상태, 진행 중 매매 · 주문 상태, 승인 대기 목록(기록용), cron · 일정, 칸반, VPN 모드 설정 · 기기 목록(세션 제외) | 토스증권 client_id/secret |
| 저장된 템플릿: 스타일 템플릿, 한도 값, 역할 · 프롬프트(SOUL 등), 스킬 | AI API 키, 구독 OAuth 토큰(access · refresh) |
| 지식 DB: 매매 기록 · 근거 · 복기 · 규칙 개선 이력 · 기억(MEMORY · 일일 메모) · 회의록 · 접속 기록 | TOTP 비밀값, 비밀번호 해시, 복구 코드 해시 |
| 설정 파일(비밀 참조 이름만, 값 없음) | 세션 키 · 세션 서명키 · 노드 키 · 백업 푸는 열쇠 · GitHub 푸시 키 |

[추정] 백업 직전에 "비밀 검사"를 돌린다: 키체인에 등록된 비밀 문자열이 백업 평문에 들어 있으면 백업을 멈추고 알린다(6.2의 자동 검사와 같은 검사기).

**private GitHub 저장소의 위험 [추정]**

| 위험 | 내용 | 대응 |
|---|---|---|
| GitHub 계정 탈취 | 저장소를 내려받거나 지움 | 클라이언트 쪽 암호화(내용 못 읽음) + GitHub 2단계 인증 + 다른 곳 사본 하나 |
| 실수로 공개 전환 | 저장소가 전 세계에 보임 | 암호화돼 있어 내용은 안전. 파일 이름 · 커밋 메시지는 보이므로 의미 없는 이름(날짜만) |
| 푸시 토큰 유출 | 서버가 털리면 그 토큰으로 백업을 덮어쓰거나 지움 | 그 저장소 하나에만 쓰는 deploy key 또는 저장소 하나로 범위를 좁힌 토큰, 키체인 보관. 기본 브랜치 보호로 강제 푸시 · 삭제 막기 |
| 크기 누적 | 암호문은 매번 통째로 바뀌어 git이 차이만 저장하지 못함 → 매일 DB 크기만큼 늘어남 | 아래 "크기 관리" |

[사실] GitHub는 50MiB 넘는 파일에 경고, 100MiB 넘는 파일은 막고, 저장소는 1GB 이하(5GB 이하 강력 권장)를 권한다. https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github

**암호화 도구**

| 도구 | 특징 | 판정 [추정] |
|---|---|---|
| `age` | 단순한 파일 암호화 도구. 받는 사람 공개키(`-r`) 또는 암호 문구(`--passphrase`)로 암호화 [사실] https://github.com/FiloSottile/age | **추천**. 서버에는 공개키만 둔다 → 서버가 털려도 지난 백업을 못 푼다 |
| `git-crypt` | git에 투명하게 붙음. 파일 이름 · 커밋 메시지 · 메타데이터는 암호화하지 않음 [사실] https://github.com/AGWA/git-crypt | 버림. 서버에 푸는 키가 있어야 하고 이름이 드러남 |
| `restic` | 암호화 · 중복 제거 백업, Linux · macOS · Windows, 백엔드는 로컬 · REST 서버 · S3 · rclone 등 [사실] https://github.com/restic/restic | GitHub를 백엔드로 쓰지 않음. 두 번째 사본(외장 디스크 · 다른 클라우드)에 적합 |

푸는 열쇠(age 개인키)는 GitHub 밖에 둔다 [추정]: 종이 인쇄(금고) + 비밀번호 관리자 + USB 하나. 서버 컴퓨터에는 두지 않는다. 열쇠를 잃으면 백업 전체를 못 쓰므로 두 곳 이상.

**주기 · 시점 [추정]**

| 언제 | 무엇 |
|---|---|
| 매일 장 마감 뒤(정규장 끝나고 체결 · 잔고 정리 뒤, 예: 16시대) | 전체 스냅샷 |
| 규칙 변경 승인 · 실전 승격 · 템플릿 저장 직후 | 작은 스냅샷(설정 · 템플릿 · 규칙) |
| 장중 | 몇 시간마다 동작 상태만(선택). 장중 큰 백업은 주문 지연을 만들 수 있어 피함 |
| 서버 끄기 · 업데이트 직전 | 전체 스냅샷 |

**일관된 스냅샷 [추정, SQLite 문서 근거]**

- DB를 쓰는 중에 파일을 그대로 복사하면 깨진 사본이 나올 수 있다. SQLite는 실행 중인 DB의 온라인 백업 API와 `VACUUM INTO`(새 파일로 정리된 사본)를 제공한다 [사실] https://www.sqlite.org/backup.html , https://www.sqlite.org/lang_vacuum.html
- 여러 DB(에이전트별 상태 · 칸반 · 지식)를 한 시점으로 맞추려면 스냅샷 동안 짧게 "쓰기 멈춤"(새 작업 받지 않기)을 걸고, 각 DB를 백업 API로 뜬 뒤 풀어 준다. 파일(기억 md · 템플릿)은 같은 멈춤 안에서 복사한다.
- 순서: 쓰기 멈춤 → DB 백업 API · 파일 복사 → 멈춤 해제 → 묶기(tar) → 압축(zstd) → 비밀 검사 → `age` 암호화 → 50MiB 아래로 나눠 커밋 · 푸시 → 결과(성공 · 크기 · 소요 시간)를 접속 기록과 하루 정리에 표시.

**크기 관리 [추정]**

1. 두 층으로 나눈다. ① 작은 층: 설정 · 템플릿 · 규칙 · 기억 md를 파일별로 암호화하되, **평문이 바뀐 파일만** 다시 암호화해 커밋(age는 같은 내용도 매번 다른 암호문이 나오므로). ② 큰 층: DB 스냅샷 묶음.
2. 큰 층은 보관 규칙: 최근 7일 매일 + 최근 8주 매주 + 매월 1개. 지난 것은 지운다.
3. git은 지운 파일도 이력에 남아 저장소가 계속 커진다. 크기를 줄이려면 이력을 다시 쓰고 강제 푸시해야 하는데, 이는 되돌릴 수 없는 작업이라 사람 확인 뒤에만 한다. 대안: 큰 층을 달마다 새 저장소(또는 새 고아 브랜치)로 돌리고 오래된 것은 사람이 지운다.
4. 오래된 매매 기록은 압축 · 요약본만 남기는 정책은 지식 DB 설계에서 정할 일(9장).

**두 번째 사본 [추정]**: GitHub만 믿지 않는다. 같은 암호문을 외장 디스크(주 1회)나 다른 클라우드(restic 백엔드)에도 둔다. 서버가 털려 푸시 키로 GitHub 백업이 덮어써져도 되살릴 곳이 있어야 한다.

**새 컴퓨터로 복원 순서 [추정]**

1. 새 컴퓨터에 가격인하 설치 → Tailscale 로그인 · 기기 승인 · tailnet lock 서명. 옛 노드는 tailnet에서 제거.
2. GitHub에서 백업을 받고 GitHub 밖에 둔 age 개인키로 풀어 복원(서버 앞에서만).
3. 서버는 **멈춤 상태로** 시작한다: 신규 주문 없음, 에이전트 쉬기.
4. 비밀 직접 재등록: 토스증권 키(새 컴퓨터 공인 IP를 토스 허용 IP에 추가, 옛 키가 털렸을 수 있으면 재발급), AI 키, 구독 OAuth 재로그인.
5. 서버 앞에서 `otp-reset`으로 TOTP 새로 등록, 비밀번호 재설정, 모든 기기 다시 로그인.
6. 진행 중이던 일 정리:
   - 백업 속 **승인 대기는 모두 "만료(복원)"로 닫는다.** 승인된 것으로 보지도, 자동 실행하지도 않는다. 필요하면 팀이 새로 판단해 새 승인 요청을 낸다.
   - 백업 속 "주문됨 · 미체결" 주문은 증권사 API로 실제 상태를 조회해 맞춘다(체결 · 취소 · 아직 열림). 맞출 때까지 P11(계좌 불일치 → 신규 주문만 정지)을 그대로 적용한다. 손절 · 청산은 허용.
   - 백업 이후 실제 잔고 · 체결이 다르면 증권사 기록을 정본으로 하고, 차이를 기록 · 복기에 남긴다.
   - cron · 일정은 복원하되, 백업 시점과 지금 사이에 놓친 일정은 한꺼번에 실행하지 않고 "놓침"으로 표시한다.
7. 내가 화면에서 "운용 재개"를 누르면(TOTP) 다시 돈다. 킬 스위치가 걸린 상태였다면 그대로 유지.

### 8.3 완성 기준 후보

- 다른 사람의 기기나 인터넷에서 VPN이 켜진 가격인하 주소를 열면 아무 응답이 없다.
- VPN을 끄면 인터넷 어디서나 열리고, 다시 켜면 다시 내 기기에서만 열린다.
- VPN을 꺼도 폰에 설치한 가격인하를 다시 설치하지 않고 그대로 쓰고 알림도 그대로 받는다.
- VPN이 꺼져 있으면 키 화면은 열리지 않는다.
- VPN이 꺼진 채로 밖에서 로그인하면 내 폰에 알림이 온다.
- 6자리 없이 비밀번호만으로는 들어올 수 없다.
- 같은 6자리를 두 번 쓰면 두 번째는 거부된다.
- 로그인한 상태라도 6자리 없이 한도 넘는 주문을 승인할 수 없다.
- 승인한 뒤 주문 내용이 바뀌면 그 주문은 나가지 않는다.
- 승인 확인이 실패하면 기록에 "거절"로 남는다.
- 기록 · 화면 · 알림 · AI 대화 어디에서도 내가 넣은 비밀키 글자가 보이지 않는다.
- 폰을 잃어버렸을 때 노트북에서 그 폰의 접속을 끊을 수 있고, 서버 컴퓨터 앞에서 인증 앱을 새로 등록할 수 있다.
- 매일 장 마감 뒤 백업이 끝났는지 하루 정리에서 보인다.
- 백업을 새 컴퓨터에 되살리면 멈춘 상태로 시작하고, 기다리던 승인은 실행되지 않는다.

### 8.4 원칙 후보 (P17~)

- **P17** 서버는 자기 컴퓨터 안에만 열고, 밖으로 나가는 길은 Tailscale 하나다. VPN을 끈 상태는 내가 직접 고른 예외이고, 그동안 민감한 기능은 막힌다.
- **P18** 위험을 키우는 행동은 건마다 본인 재확인, 위험을 줄이는 행동은 바로 된다.
- **P19** 승인 확인 실패 · 모르는 결정은 언제나 거절이다. 실패를 "답 없음"으로 바꾸지 않는다.
- **P20** 승인 경로가 막힌 것이 감지되면 답 없음 처리는 더 보수적으로(신규 매수 없음, 손절 · 청산만).
- **P21** AI 에이전트는 비밀키를 보지 못하고, AI의 말은 승인이 아니다. 승인의 정본은 서버 기록뿐이다.
- **P22** 비밀키와 인증 비밀값은 백업 · 화면 · 기록 어디에도 남기지 않고, 되살릴 때는 사람이 다시 넣는다.

## 9. 확인 못 한 것

- `*.ts.net` 주소의 홈 화면 PWA에서 iOS · 안드로이드 웹 푸시 구독 · 수신이 실제로 되는지, Serve ↔ Funnel 전환 뒤에도 구독이 유지되는지: 실기기 확인 필요(근거는 표준 · 문서에서 끌어낸 추정).
- 폰이 tailnet에 없을 때 푸시 수신이 되는 것은 Push API 구조에서 끌어낸 추정. 알림 클릭으로 열 때 VPN 온디맨드가 제때 붙는지 실기기 확인 필요.
- Funnel 대역폭 제한 수치, 베타 종료 시점, Windows · macOS 앱 변형별 Funnel 동작, 앱이 관리자 권한 없이 Serve/Funnel을 전환하는 방법(예: Linux operator 설정 · LocalAPI).
- iOS 웹 푸시의 HTTPS 요구를 Apple 1차 문서로 직접 확인하지 못함(MDN · W3C 보안 컨텍스트 요구로 갈음).
- NIST SP 800-63B-4의 AAL2 비활동 시한 숫자, OTP 연속 실패 상한 숫자: 1차 페이지에서 찾지 못함(전체 24시간 · OTP 1회 사용 · 피싱 비저항만 확인).
- 구글 OTP 클라우드 동기화의 세부 동작은 구글 지원 페이지 일부 + 2차 출처.
- 토스증권 허용 IP · 토큰 규칙: 2차 출처(블로그)만. 공식 문서와 대조 필요.
- Cloudflare Tunnel의 TLS 엣지 종료 세부: 2차 출처만.
- 화면 없는 Linux에서 키 보관 최종 방식(마스터 비밀번호 vs systemd 자격 증명), 서버 재시작 뒤 세션 유지 여부: 사람이 정할 일.
- 끈 상태 알림 시각, 서버 재시작 때 모드 유지 여부, 세션 · 시도 제한 숫자는 모두 제안값.
- Hermes `agent/redact*.py`의 실제 규칙, Hermes · 플러그인 쪽 시도 제한 유무는 읽지 않음. DeskRPG 로그인 시도 제한이 없다는 판단은 grep 기준.
- 백업: GitHub 이력 정리(강제 푸시) 없이 크기를 관리하는 최종 방식, 장중 상태 백업 주기, 오래된 매매 기록 요약 정책, 두 번째 사본 위치는 사람이 정할 일. 복원 뒤 증권사 주문 · 체결 조회 API로 상태를 맞출 수 있는지는 토스증권 API 문서로 확인 필요.
- VPS가 주 서버일 때 "서버 컴퓨터 앞 OTP 초기화"가 클라우드 웹 콘솔 접근이 되므로, 그 클라우드 계정 보안 수준은 따로 정해야 함.
- REA CLI는 돌리지 않았다. 필요한 사실은 기존 분석 문서와 원본 문서 · 소스 grep으로 충분했다.
